Point avagama.app at your EC2 instance

Map a real domain + HTTPS onto your running services — frontend on :3000, backend on :5000 — using Nginx as a reverse proxy and Let's Encrypt for SSL.

⚠ Read this first — .app forces HTTPS. The .app TLD is on the browser HSTS preload list, so Chrome, Safari, Firefox and Edge will only ever load it over HTTPS — plain http://avagama.app will refuse to connect. That means SSL (Step 6) is mandatory; the site simply will not work until the certificate is installed. Everything below is ordered so HTTPS is ready before you rely on the domain.

0 · How it will fit together

Right now browsers hit your app by IP and port. We put Nginx in front on ports 80/443. Nginx terminates HTTPS and forwards (reverse-proxies) each hostname to the right local port. Your Node apps keep running exactly as they are on 3000 and 5000 — you don't expose those ports publicly any more.

┌───────────────── EC2 (13.207.66.222) ─────────────────┐ Browser ──HTTPS──▶ │ Nginx :443 / :80 │ avagama.app │ ├─ avagama.app, www.avagama.app ─▶ 127.0.0.1:3000 │ (frontend) api.avagama.app │ └─ api.avagama.app ─▶ 127.0.0.1:5000 │ (backend) └────────────────────────────────────────────────────────┘
Run every command below over SSH on the EC2 box: ssh -i your-key.pem ubuntu@13.207.66.222 (user is ubuntu for Ubuntu AMIs, ec2-user for Amazon Linux). Commands assume Ubuntu; for Amazon Linux swap apt → dnf/yum.

1 · Lock the public IP with an Elastic IP

A normal EC2 public IP changes every time the instance stops/starts. If that happens after you set DNS, your domain breaks. Attach a free Elastic IP so the address is permanent.

a
AWS Console → EC2 → Network & Security → Elastic IPs → Allocate Elastic IP address → Allocate.
b
Select it → Actions → Associate → choose your instance → Associate.
c
Note the Elastic IP. Use that IP in the DNS step. It may differ from 13.207.66.222 — if so, use the new one everywhere below.
If 13.207.66.222 is already an Elastic IP, just confirm it's associated and keep using it.

2 · Create DNS records at your registrar

Wherever you registered avagama.app (Google Domains/Squarespace, GoDaddy, Namecheap, Cloudflare, or AWS Route 53), open its DNS settings and add three records pointing to your (Elastic) IP:

TypeName / HostValueTTL
A@ (root)13.207.66.222300
Awww13.207.66.222300
Aapi13.207.66.222300
Some registrars don't allow an A record on @ — in that case use an ALIAS/ANAME to the IP, or if you're on Route 53 use an A record · Alias. On Cloudflare, set the proxy status to DNS only (grey cloud) while you issue the certificate, or Certbot's HTTP check can fail.

Check propagation (wait 5–30 min; occasionally longer):

dig +short avagama.app
dig +short www.avagama.app
dig +short api.avagama.app
# each should print your Elastic IP

3 · Open ports 80 & 443 in the Security Group

EC2 → your instance → Security tab → click the Security Group → Edit inbound rules → add:

TypeProtocolPortSourceWhy
HTTPTCP800.0.0.0/0, ::/0Certbot challenge + HTTP→HTTPS redirect
HTTPSTCP4430.0.0.0/0, ::/0Real traffic
SSHTCP22your IPKeep as-is
Security win: once Nginx is proxying, you can remove the public inbound rules for 3000 and 5000. Those apps only need to be reachable from Nginx on the same box (127.0.0.1), not from the internet.

4 · Install Nginx

sudo apt update
sudo apt install -y nginx
sudo systemctl enable --now nginx
# visit http://13.207.66.222  — you should see the Nginx welcome page

5 · Nginx reverse-proxy config

Create one site config that handles both the frontend and the API subdomain. (This is the HTTP version; Certbot rewrites it for HTTPS in Step 6.)

sudo nano /etc/nginx/sites-available/avagama

Paste:

# ---- Frontend: avagama.app + www ----
server {
    listen 80;
    server_name avagama.app www.avagama.app;

    location / {
        proxy_pass         http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header   Host              $host;
        proxy_set_header   X-Real-IP         $remote_addr;
        proxy_set_header   X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header   X-Forwarded-Proto $scheme;
        # websockets / HMR, harmless for prod:
        proxy_set_header   Upgrade           $http_upgrade;
        proxy_set_header   Connection        "upgrade";
    }
}

# ---- Backend API: api.avagama.app ----
server {
    listen 80;
    server_name api.avagama.app;

    client_max_body_size 25m;   # allow file/invoice uploads

    location / {
        proxy_pass         http://127.0.0.1:5000;
        proxy_http_version 1.1;
        proxy_set_header   Host              $host;
        proxy_set_header   X-Real-IP         $remote_addr;
        proxy_set_header   X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header   X-Forwarded-Proto $scheme;
        proxy_read_timeout 300s;   # long-running agent/OCR calls
    }
}

Enable it and reload:

sudo ln -s /etc/nginx/sites-available/avagama /etc/nginx/sites-enabled/
sudo rm -f /etc/nginx/sites-enabled/default   # drop the welcome page
sudo nginx -t          # test config — must say "syntax is ok"
sudo systemctl reload nginx
Prefer serving the built frontend as static files instead of proxying a dev server? Point the frontend location / at your build output instead: root /var/www/avagama/dist; try_files $uri /index.html; and drop the proxy_pass. Keep the proxy version if that's how you run :3000 today — don't change two things at once.

6 · Get HTTPS with Certbot (Let's Encrypt)

Free, auto-renewing certificates. Install and let Certbot edit your Nginx config for all three hostnames:

sudo apt install -y certbot python3-certbot-nginx

sudo certbot --nginx \
  -d avagama.app -d www.avagama.app -d api.avagama.app \
  --redirect --agree-tos -m you@youremail.com --no-eff-email

--redirect makes Certbot add the HTTP→HTTPS redirect automatically. When it finishes, sudo nginx -t && sudo systemctl reload nginx.

Auto-renewal is installed as a systemd timer. Confirm it works: sudo certbot renew --dry-run.
Certbot must reach your server over port 80 at those exact hostnames, so DNS (Step 2) must have propagated and port 80 must be open (Step 3) before you run this. If it fails with "challenge failed", re-check both.

7 · Repoint the frontend at the new API URL & rebuild

Your frontend currently calls the API by IP:port. Update its environment to the HTTPS API domain, then rebuild — a .app page served over HTTPS cannot call an http:// or mixed-content API, so this must change.

In the frontend project's .env (this repo uses VITE_ vars — see .env.example):

VITE_API_URL=https://api.avagama.app
VITE_PUBLIC_APP_URL=https://avagama.app
# from the frontend directory on the server (or rebuild locally & upload dist)
npm run build
# then restart however you serve :3000 (see Step 9)
Agent embed allow-list: you earlier set some embedded agents' CSP frame-ancestors to include https://avagama.dev / localhost. If you're moving to avagama.app, add https://avagama.app to those agents' frame-ancestors too, or the inline embeds will be blocked on the new domain.

8 · Allow the new domain in backend CORS

The backend must accept browser requests coming from https://avagama.app. Update its allowed-origins list (name varies by framework — CORS_ORIGIN, an allowlist array, etc.) to include:

https://avagama.app
https://www.avagama.app

Then restart the backend. If cookies/sessions are used cross-site, also ensure cookies are Secure + SameSite=None.

Teammate note (backend round 2): a backend session reported new API behaviour is live on :5000 (chat guardrails field, a finance connector, stricter run validation returning 400 with issue_details, RFP 404 {exists:false} before creation). None of it changes these domain steps, but keep it in mind when you next wire those endpoints — the contract is in the backend's AVAGAMA_ORCHESTRATION_API_CONTRACT.txt, section F.

9 · Keep the apps running (survive reboots)

Make sure :3000 and :5000 restart on crash/reboot. If you already use PM2, just make it persistent:

pm2 start npm --name avagama-frontend -- run start   # or your serve command
pm2 start npm --name avagama-backend  -- run start   # in the backend dir
pm2 save
pm2 startup        # run the line it prints, then: pm2 save

Check: pm2 status. (If you use systemd services or Docker instead, keep those — Nginx proxies to the port regardless of how it's run.)

10 · Verify

# HTTP should 301-redirect to HTTPS
curl -I http://avagama.app

# HTTPS frontend should return 200
curl -I https://avagama.app

# API over HTTPS (hit a real health/known route)
curl -I https://api.avagama.app

# certificate covers all three names
echo | openssl s_client -servername avagama.app -connect avagama.app:443 2>/dev/null | openssl x509 -noout -subject -dates

Then in a browser: https://avagama.app loads the app, the network tab shows calls going to https://api.avagama.app with no mixed-content or CORS errors.

Troubleshooting

SymptomLikely cause → fix
Browser: "can't connect" to avagama.appDNS not propagated, or Step 6 not done (.app needs HTTPS). Re-check dig + that Certbot succeeded.
Certbot "challenge failed"Port 80 closed in Security Group, DNS not pointing to this IP yet, or Cloudflare proxy on (grey-cloud it).
502 Bad GatewayThe app on 3000/5000 isn't running or crashed. pm2 status, pm2 logs.
Frontend loads but API calls fail (CORS)Step 8 — add https://avagama.app to backend allowed origins, restart.
"Mixed content" blocked in consoleFrontend still calling http://…:5000. Step 7 — set VITE_API_URL=https://api.avagama.app and rebuild.
Embedded agent panel blank on new domainAdd https://avagama.app to that agent's CSP frame-ancestors.
413 Request Entity Too Large on uploadRaise client_max_body_size in the api server block.
